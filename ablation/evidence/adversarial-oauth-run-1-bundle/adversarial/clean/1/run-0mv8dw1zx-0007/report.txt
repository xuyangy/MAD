      recordRefund does not await the ledger.append call, unlike recordCharge which does await it.

      In recordCharge, `await ledger.append(...)` ensures the async operation completes (and any rejection is surfaced/caught) before the function resolves. In recordRefund, `ledger.append(charge.account, -charge.cents)` is called without `await`. Since recordRefund is declared `async` and returns `Promise<void>`, callers who `await recordRefund(...)` will see it resolve immediately once the synchronous part finishes, without waiting for the underlying append to actually complete. This means: (1) callers cannot rely on the refund being durably recorded by the time the promise resolves, leading to potential race conditions where subsequent reads see stale ledger state; (2) if `ledger.append` rejects (e.g., due to a transient DB error), the rejection becomes an unhandled promise rejection instead of propagating to the caller of recordRefund, so the failure is silently swallowed rather than causing recordRefund's returned promise to reject. This is a correctness/error-handling bug that could cause silent data loss of refund records.
